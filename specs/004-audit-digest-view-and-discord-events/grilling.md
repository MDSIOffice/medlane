# Grilling: 004-audit-digest-view-and-discord-events

**Q1. Storing full email HTML per recipient in the audit log — bloat?**
A. Not per recipient. One R2 object per digest run per role (the HTML is identical for all
recipients of a role). ~3 objects/day, ~15 KB gzipped each. The audit rows only carry a uuid.

**Q2. R2 objects for digest messages accumulate forever.**
A. ~16 MB/year — negligible against a 500 GB bucket. Documented as a follow-up (lifecycle rule
or sweep). Not worth a pruning code path now.

**Q3. `iframe srcdoc` with the stored HTML — XSS / injection?**
A. The HTML is generated by our own `digestEmailHtml`/`brandedEmailHtml` from structured data
that's already `escapeHtml`'d at build time. Rendered in `<iframe sandbox="">` — no scripts, no
same-origin, no forms. Even if a digest string slipped an unescaped tag, it can't reach the
parent document or the user's session.

**Q4. `readDigestMessageSnapshot` takes an `id` from the query string → path traversal into R2?**
A. `id` is regex-validated to a uuid shape (`/^[0-9a-f-]{36}$/i`) before being interpolated
into the key. No `/`, `.`, `..` possible. Key is also prefixed with the state key.

**Q5. Adding `payments` to `DISCORD_EVENT_MODULES` means every collection save now pages the
entire payments table for the before-diff. Cost?**
A. `supabaseFetchAll` at 1000/page. A collection action already does several round-trips; one
more paged read is acceptable and bounded. If payments grows huge this is the first thing to
revisit (e.g. fetch only the incoming record_keys), but it's correct as-is.

**Q6. Double-posting: inventory PO approve posts explicitly in its endpoint. If the client then
does a full `saveData()` that includes the approved PO, does the state-PUT poster post again?**
A. No. `eventBeforeRows` is read from the DB immediately before the write, so it already
reflects `status: "Approved"` set by the dedicated endpoint moments earlier →
`statusChanged("status")` is false → no second post. Same protection for transfers/collections.

**Q7. What if `beforeRows` is truncated (PostgREST max-rows cap) and an existing transfer isn't
in the page — does it get mis-posted as "New Pending Transfer"?**
A. That was the risk with the state-PUT path's single-page `supabaseFetch`. Fixed: the poster
is now fed a dedicated `supabaseFetchAll` scoped to just the event modules. The circuit-breaker
counts still use the capped single page (unchanged; undercounting there only makes it *less*
likely to trip, which is safe).

**Q8. `recordSystemLog` gained an `extra` spread. Could a caller clobber `date`/`user`/`action`?**
A. `extra` is spread last, so in principle yes — but the only caller passing it is
`sendResendEmail` with `{ digestMessageId }`. Guarded with `typeof extra === "object"`. Not a
general-purpose hole; if it grows, add a key allowlist.

**Q9. Transfer "received" match is `/received/i` on `record.status` — does "For Receiving"
falsely match?**
A. `statusChanged("status")` must also be true. A transfer sitting at "For Receiving" from
creation never transitions *to* "For Receiving", so the change-guard blocks it. The create
branch already excludes `/received|cancelled/i`. New status values that legitimately contain
"received" (`Partially Received`, `Confirmed Received`) are exactly what we want to post.

**Q10. Discord post latency added to the approve endpoints (no `ctx.waitUntil` in `fetch`).**
A. One webhook POST (~200-400 ms) on approval actions, which are already multi-request
operations a human just clicked. `postWorkflowEventToDiscord` swallows failures so it can't
extend an error path. Acceptable; matches how `createBackup` already posts inline.

**Q11. Verification without a local env.**
A. `node --check` + `wrangler deploy --dry-run` pre-deploy. Post-deploy: (a) open a digest
`Email sent` row in Audit Logs → Details → View message sent; (b) run one transfer through
dispatch/receive, approve a payment request, change a collection status, approve a PO and a
stock receipt, and confirm one Discord post each with no duplicates.
